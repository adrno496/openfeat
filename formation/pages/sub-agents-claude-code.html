Sub-agents Claude Code — créer des agents personnalisés (tutoriel)

Mis à jour mai 2026 · Lecture 11 min

Un sub-agent Claude Code est un sous-processus qui vit dans son propre contexte, avec sa propre identité et ses propres permissions. Il sert à isoler une tâche longue ou risquée du contexte principal, à paralléliser plusieurs investigations, ou à spécialiser certains rôles avec des permissions restreintes.

Pourquoi utiliser un sub-agent

3 cas où un sub-agent est meilleur qu'une session principale qui s'étire :

  • Isolation — tu refactor 10 fichiers, tu ne veux pas polluer ta session principale avec 50 lectures de code
  • Parallélisation — tu explores 3 hypothèses pour un bug, 3 sub-agents en parallèle gagnent du temps
  • Spécialisation — un sub-agent code-reviewer a accès uniquement à Read, Bash, Grep (pas d'écriture)

Anatomie d'un sub-agent custom

Les sub-agents personnalisés se définissent dans :

  • ~/.claude/agents/<nom>.md — global, perso
  • .claude/agents/<nom>.md — projet, commité

Frontmatter YAML obligatoire :

---
name: code-reviewer
description: Review du code modifié sur la branche courante. Cherche bugs, failles, duplications.
model: claude-sonnet-4-6
tools: Read, Bash, Grep
---

Tu es un reviewer de code expérimenté. Quand on t'invoque :

1. Identifier les fichiers modifiés via `git diff main`
2. Lire chaque fichier en intégralité
3. Pour chaque, signaler :
   - bugs potentiels (null pointer, race condition, off-by-one)
   - failles de sécurité (XSS, SQL injection, secrets en dur)
   - duplications de code
   - patterns incohérents avec le reste du projet

Ne pas modifier le code. Juste rapporter.

Champs critiques du frontmatter :

  • name — identifiant invocable
  • description — ce que fait l'agent (utilisée pour le triggering)
  • model — modèle utilisé (sonnet/opus/haiku, indépendant de la session principale)
  • tools — whitelist explicite des outils accessibles

Choix du modèle par sub-agent

Une optimisation puissante : utiliser un modèle moins cher pour les sub-agents qui n'ont pas besoin de raisonnement avancé.

  • Haiku — sub-agent explorer (recherche dans codebase, traitement de texte)
  • Sonnet — sub-agent code-reviewer ou security-auditor (équilibre)
  • Opus — sub-agent qui doit raisonner sur architecture ou stratégie

Économie typique : un sub-agent explorer en Haiku coûte ~5x moins qu'en Opus pour une qualité équivalente sur sa tâche spécifique.

3 sub-agents prêts à l'emploi

1. explorer — recherche read-only

---
name: explorer
description: Recherche read-only dans la codebase. Renvoie chemins, lignes, et extraits pertinents.
model: claude-haiku-4-5-20251001
tools: Read, Grep, Glob, Bash
---

Tu es un agent de recherche read-only. Tu n'écris jamais.

Pour chaque demande :
1. Glob ou Grep pour localiser
2. Lis les fichiers pertinents en partie ciblée (pas tout le fichier)
3. Rapporte sous format :
   - chemin/du/fichier.ext:ligne
   - 3 lignes de contexte
   - Pertinence : forte / moyenne / faible

2. code-reviewer — review de PR

Vu plus haut. Modèle Sonnet, tools Read, Bash, Grep.

3. security-auditor — audit OWASP

---
name: security-auditor
description: Audit de sécurité focalisé OWASP top 10 sur fichiers de la branche.
model: claude-sonnet-4-6
tools: Read, Grep, Bash
---

Tu es un auditeur de sécurité focalisé sur les vulnérabilités courantes.

Vérifier les patterns :
- Injections (SQL, command, NoSQL)
- XSS (innerHTML, dangerouslySetInnerHTML)
- Secrets (sk_live_, service_role, api_key)
- Auth/Autorisation (endpoints sans check)
- CSRF / clickjacking

Communication parent → sub-agent

L'agent parent invoque un sub-agent avec un prompt complet (puisque le sub-agent ne voit pas le contexte parent).

"Lance un sub-agent code-reviewer pour reviewer la branche feat/auth. Il doit me rapporter en moins de 200 mots."

Le sub-agent reçoit son prompt + sa définition (frontmatter + body), exécute, retourne un message au parent. Pas de chaînage : un sub-agent ne peut pas appeler d'autres sub-agents.

Parallélisation

Tu peux lancer plusieurs sub-agents en parallèle dans le même message :

"Lance en parallèle :
- sub-agent explorer : où est défini le composant UserProfile ?
- sub-agent explorer : quels endpoints REST utilisent UserProfile ?
- sub-agent explorer : quels tests couvrent UserProfile ?

Synthétise les 3 réponses."

Trois investigations en parallèle, gain de temps net (~3x sur le wall-clock).

Limites et pièges

  • Le sub-agent ne sait rien du parent — tu dois lui réécrire le contexte nécessaire
  • Consommation tokens — chaque sub-agent = nouvelle conversation = nouveau contexte chargé
  • Pas de chaînage — sub-agent → sub-agent impossible, à orchestrer côté parent
  • Permissions silencieuses — si un sub-agent veut un tool qu'il n'a pas dans tools, il échoue silencieusement
  • Sur-utilisation — pour des tâches courtes (< 5 min), la session principale suffit, le sub-agent ajoute de l'overhead

Quand préférer slash command, skill ou sub-agent

  • Slash command : workflow rapide, invocation explicite, dans la session courante
  • Skill : auto-déclenché par contexte, vit dans la session courante
  • Sub-agent : tâche longue / risquée, contexte isolé, permissions restreintes
