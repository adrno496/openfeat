Tutoriel Skills Claude Code — créer un skill custom auto-déclenché

Mis à jour mai 2026 · Lecture 10 min

Un skill Claude Code est un module markdown qui enseigne à l'assistant à exécuter une tâche spécifique. Sa caractéristique unique : il peut s'auto-déclencher quand le contexte le justifie, sans que tu le demandes explicitement. Bien conçu, un skill est un super-pouvoir permanent dans tes projets.

Skill vs slash command vs sub-agent : la cartographie

  • Skill : auto-déclenché selon le contexte (via le champ description). Vit dans la session courante.
  • Slash command : invoquée explicitement par /nom. Vit dans la session courante.
  • Sub-agent : invoqué explicitement, vit dans son propre contexte isolé.

Si tu veux automatiser un comportement récurrent qui doit s'appliquer dès que la situation se présente (audit RLS sur une migration Supabase, génération de commit message après git add, etc.) : skill.

Structure d'un skill

Les skills se placent dans :

  • ~/.claude/skills/<nom>/SKILL.md — global, perso
  • .claude/skills/<nom>/SKILL.md — projet, commité

Structure type d'un skill professionnel :

.claude/skills/csp-auditor/
├── SKILL.md              # Le contrat (< 100 lignes)
├── reference/
│   └── patterns.md       # Patterns à appliquer (chargés au besoin)
└── examples/
    ├── good-policy.txt
    └── bad-policy.txt

Le frontmatter : 80 % du résultat

Le champ description dans le frontmatter YAML est critique. C'est ce que Claude Code lit pour décider si le skill s'applique au contexte courant.

Mauvais (trigger trop vague) :

---
name: csp-auditor
description: Outil pour CSP
---

Bon (trigger précis avec mots-clés et patterns) :

---
name: csp-auditor
description: Audite une politique CSP (Content-Security-Policy) et détecte
  les directives dangereuses (unsafe-inline, unsafe-eval, wildcards). Trigger
  quand l'utilisateur mentionne CSP, Content-Security-Policy, csp.config,
  header de sécurité, ou édite un fichier *.csp ou contenant l'expression
  Content-Security-Policy.
---

La règle : inclure 4 à 8 mots-clés concrets + patterns de fichier + expressions naturelles que l'utilisateur tape. Plus tu donnes de signaux, plus le triggering est précis.

Le body : structurer pour la lecture rapide

# CSP Auditor

## Quand t'appliquer
- Édition d'un fichier contenant une politique CSP
- Demande explicite d'audit CSP

## Méthode
1. Identifier la chaîne CSP complète
2. Parser les directives
3. Signaler les anti-patterns
4. Proposer une politique alternative si critique

## Règles dures
- unsafe-inline dans script-src → critique (XSS)
- unsafe-eval → critique (exec arbitraire)
- wildcard * dans script-src → critique (bypass)

## Format de sortie
Pour chaque issue :
- ligne X-Y : description
- Suggestion : fix concret

## Cas où NE PAS appliquer
- Fichier dans node_modules/ ou .tmp/
- CSP en mode Report-Only marquée "draft"

Sections numérotées, courtes, lisibles en 30 secondes. Pas de prose longue.

Tester le triggering

Avant de publier un skill, écris une suite de prompts de test et mesure le ratio de déclenchement.

Exemple de tests pour csp-auditor :

  • "Audit la CSP de ce site" → doit trigger ✓
  • "Lis ce fichier csp.config" → doit trigger ✓
  • "Vérifie le header Content-Security-Policy" → doit trigger ✓
  • "Crée une fonction de validation" → ne doit PAS trigger ✓
  • "Décris ce projet" → ne doit PAS trigger ✓

Vise 4/5 sur les "OUI" et 0/5 sur les "NON". Si moins, retravaille la description.

Skills composables avec ressources externes

Un skill complexe sans ressources externes devient un mur de markdown de 200+ lignes, inmaintenable. La solution : composer.

Dans SKILL.md :

## Méthode
Pour chaque table à auditer :
1. Vérifier l'application du Pattern: user_owns_row (voir reference/patterns.md)
2. Si le pattern n'est pas appliqué, signaler.

Dans reference/patterns.md :

# Patterns RLS du projet

## Pattern: user_owns_row

```sql
ENABLE RLS;
CREATE POLICY "owner_select" FOR SELECT USING (auth.uid() = user_id);
...
```

Claude Code charge la ressource externe à la demande, pas avant. Économie de contexte massive.

Distribuer ton skill

  • Privé (perso) : ~/.claude/skills/<nom>/, dans tes dotfiles
  • Équipe : .claude/skills/<nom>/ commité dans le repo projet
  • Public : repo GitHub avec README + LICENSE, install via git clone

Erreurs fréquentes

  • Description trop vague → trigger raté
  • Description trop large → trigger partout, pollution contexte
  • Body de 300 lignes → c'est un sub-agent qu'il te faut
  • Pas de "Cas où NE PAS appliquer" → faux positifs
  • Ressources externes pas référencées dans le body → Claude Code ne les lit jamais

Exemple complet : skill commit-conventional

---
name: commit-conventional
description: Génère un commit message au format Conventional Commits depuis le diff staged.
  Trigger quand l'utilisateur demande "génère un commit", "commit message",
  "écris-moi un commit", après git add ou git diff --staged.
---

# Commit Conventional

## Méthode
1. Lire git diff --staged
2. Identifier le type (feat, fix, refactor, etc.)
3. Identifier le scope
4. Rédiger description courte impérative

## Règles dures
- Format : type(scope): description
- Max 72 caractères
- Pas de point final
- Impératif présent ("add" pas "added")

## Format de sortie
Affiche uniquement le message, sans explication, sans guillemets.

## Cas où NE PAS appliquer
- Si rien n'est staged → demander de stager
- Si l'utilisateur demande explicitement un autre format
